# 规则卡 · 架构深化

面向交稿之后仍能讲清楚、也能继续做的一层设计。核心不变：**散文提议结构，符号系统下结论**。UI 上的「多人」目前只是前端循环调用单人接口；深化要把「订单会话」做成一等公民。

## 1. 现在卡在哪

| 层级 | 现状 | 真实订票还缺什么 |
|---|---|---|
| 会话 | Demo 里 `people[]`，每人调一次 `compileAndRun` | 订单级对象：出行人、权益、日期、主预订人 |
| 编译 | 整页抽一次规则，对所有人复用 | 对（好）；但缺「规则版本 / 置信度 / 未覆盖句」 |
| 执行 | 票种三档 + 互斥优惠 | 缺「1 成人限带 N 免票童」、日历日（六一家长半价） |
| 对照 | 种草 / 首个数 / 消融 | 缺「订单级种草冲突」：任一童被忽悠就算冲突 |
| 嵌入 | 独立页 | 缺购票页 SDK：输入人列表，输出每人票种 + 阻断理由 |

一句话：编译层已经像编译器，**会话层和产品契约还像脚本**。

## 2. 目标分层（建议定稿）

```
┌─────────────────────────────────────────────┐
│  体验层 Presentation                          │
│  购票页模块 / LIVE DEMO / 客服侧查条款        │
├─────────────────────────────────────────────┤
│  会话层 Session（新增一等公民）                │
│  Party = { travelers[], visit_date, channel }│
│  输出 OrderCard = 每人票种 + 本单汇总 + 阻断  │
├─────────────────────────────────────────────┤
│  编译层 Compile                               │
│  页面+种草 → RuleIR（可校验中间表示）         │
│  附：coverage、confidence、citations          │
├─────────────────────────────────────────────┤
│  执行层 Execute                               │
│  RuleIR × Traveler × Context → TicketJudgment│
├─────────────────────────────────────────────┤
│  对照层 Critique                              │
│  朴素读法 / 消融 /（可选）模型草案            │
└─────────────────────────────────────────────┘
```

上下游只通过 **RuleIR** 和 **OrderCard** 两个契约说话。换抽取器、换 UI、换求解器，不互相穿透。

## 3. 三个该想深的点

### 3.1 RuleIR：别停在「抽几个字段」

现在的 `rule` dict 够演示，不够演进。建议显式成中间表示：

- **bands**：身高/年龄区间列表（含开闭区间），而不是一对 `free_lt/half_lt`
- **combinator**：`height | age | either | both`（已有）
- **quotas**：`adult_can_bring_free_children: 3`（国博/科技馆类）
- **calendar**：节日覆盖规则（六一随同家长半价）——默认空
- **citations**：每个字段挂触发句 index（已有 clause_*，应结构化）
- **coverage**：页面里有多少「疑似票务句」未被任何槽位消费

`coverage < 1` 时，UI 应显示「条款可能未读全」，而不是假装全绿。这是对评委「诚实边界」的产品化。

### 3.2 会话执行：从 map(人) 到 reduce(单)

今日 Demo：

```
for person in party: compileAndRun(page, person)
```

目标：

```
rule = compile(page, promo)          # 一次
for person in party:
    judgments.append(execute(rule, person, ctx))
order = aggregate(judgments, promo)  # 种草冲突、限额、是否可点预订
```

`aggregate` 要回答的业务问题：

1. 本单是否允许点「立即预订」（有全票缺口？有种草高冲突？）
2. 免票童是否超过「每成人可带 N 人」
3. 主预订人是否满足陪同约束（未满 14 须成人代约）

这些**不是**再抽一次散文，而是在执行层用已编译规则做约束传播——更接近 ChinaTravel 里「符号校验」那一段。

### 3.3 置信度与人机回路

离线正则会在新句式上静默错。深化不靠「换更大模型当真理」，而靠：

| 信号 | 用途 |
|---|---|
| schema 校验失败 | 直接拒出，走修补或人工 |
| coverage 低 | 提示「有句子没进规则」 |
| 模型草案 ≠ 离线抽取 | 标黄，执行仍用离线，除非人工选用草案 |
| heldout 错因上升 | 标注同学优先换官网原文 |

产品形态：预订前卡上多一枚「依据充分 / 需人工确认」，比再堆一个聊天框更像交易系统。

## 4. 嵌入携程页时的最小 SDK

不要把 Demo 整页塞进 App。对外只暴露：

```ts
type Traveler = { id: string; age: number; height_m: number; tags?: string[] }
type OrderInput = { page_text: string; promo_text?: string; travelers: Traveler[]; visit_date?: string }
type OrderCard = {
  rule_id: string
  per_person: { id: string; ticket: "free"|"half"|"full"; clause: string }[]
  summary: { free: number; half: number; full: number }
  blockers: { code: string; message: string }[]  // promo_conflict | quota | escort
  release: string
}
function buildOrderCard(input: OrderInput): OrderCard
```

购票页负责人列表与下单；规则卡只返回 **能不能买对**。库存、支付、风控仍在主链路。

## 5. 与「再做一个旅行 Agent」的分界

| 做 | 不做 |
|---|---|
| 交易前规则澄清 | 多日行程规划 |
| 条款 → 可执行 IR | 用模型直接说「你免票」 |
| 订单级汇总与阻断 | 预测票是否抢得到 |
| 留出集与错因 | 假装全国准确率 |

深化是把同一把刀磨快，不是换成瑞士军刀。

## 6. 建议落地顺序（交稿后 / 若还有窗口）

1. **P0 会话 API**：`build_order_card(party)`，Demo 改为调这一层（行为与现在多人 UI 对齐，但架构立正）。
2. **P0 coverage**：未消费句子打进 `OrderCard.warnings`。
3. **P1 quotas / escort**：科技馆、国博类「成人带领」进 RuleIR。
4. **P1 日历钩子**：接口留 `visit_date`，规则可空。
5. **P2 模型草案对照面板**：仅答辩/调试模式默认展开。

前两步不增加用户打字，却能把「像作品」变成「像可嵌入模块」。
